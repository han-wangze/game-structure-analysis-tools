# 手游市场结构分析脚本

| 脚本 | 解决什么 | 输入 → 输出 |
|---|---|---|
| `genre_analysis.py` | 按品类 / 题材 × 年份算齐结构指标（集中度 / 吸量效率 / 新品 / 存量 / Top10） | 榜单导出 csv × N → 5 张底表 Excel + 对比图 |
| `market_structure_analysis.py` | 把逐年算的指标连成趋势，并给出**产品模型交叉 / 发行商与出海 / 进入判断** | 榜单导出 csv × N → 5 张底表 Excel |
| `cohort_tracking.py` | 用产品 ID 跨年连接，看**新品队列进入头部的比例 / 头部留存 / 换血** | 榜单导出 csv × N → 4 张底表 Excel |
| `concentration_cr.py` | 按国家 × 品类 × 年份计算 CR4/CR5/CR10 与 Top10 产品名单 | 分析数据集 xlsx → 格式化 Excel 报告（收入 / 下载两维度） |
| `lifecycle_classify.py` | 给产品打「始终 / 曾经 / 从未在榜」标签，输出在榜年份记录 | 分析数据集 xlsx → 在榜产品明细 xlsx |

---

## 0. 数据边界与口径（先读这一节）

榜单导出的样本框决定了哪些结论能成立。这几条写在代码里，不靠人记。

1. **总量与份额只能用排序轴。** 榜单是「按某一个指标排序后导出的」，所以：按收入导出的样本里，总收入基本完整，但「高下载低收入」的纯广告产品被截断 ⇒ **它的下载量是系统性低估**；按下载导出的样本反之。另一轴只能出**样本内结构**结论（表里标 `sample_only`），不能当品类级。
   - 实测影响：某品类 2025 年收入 CR5，在不过滤时是 83.0%，过滤后是 87.0%——差的 4 个百分点全在非游戏产品上。
2. **必须过滤 `Category != 'Games'`。** 实测下载榜样本里有 3.6% 的非游戏产品，而它们同样带着品类 / 题材标签，不滤会污染分母。
3. **跨年在榜一律用固定 Top N 排名口径**，不用「是否出现在导出文件里」——各年榜单深度逐年变化（实测某品类每年 1,641 → 629 行），用文件出现与否会把「榜单变浅」误判成「产品掉榜」。
4. **DAU 只用于头部子样本**（覆盖率按下载五分位：最低档 8.9%、最高档 70%），不做主指标；ARPDAU 覆盖率 3%–15%，同理。
5. **不跨数据集拼接。** 每个导出各自跑，结论不跨集合并；产品 ID 只在同一个数据集内跨年有效。
6. **不把不同口径的维度排成一张座次。** 收入榜导出的品类与下载榜导出的品类分开呈现，各自内部可比。

## 1. genre_analysis.py — 品类 / 题材结构分析

**为什么需要**：报告要判断「某个品类或题材值不值得进入」，靠的是市场结构而不是总量规模。集中度、分层增长贡献、新品渗透与变现、存量生命周期这些结构指标没法用透视表一次算出来，故写成脚本按「品类 × 年份」批量算齐，输出分页签底表供报告正文取数。

**做什么**（对每个品类 × 年份各算一遍）

- **集中度**：CR3 / CR5 / CR10、头部 / 中腰部 / 尾部（40% / 70% 阈值）分层增长贡献、Top10 产品下载与收入双维度贡献；
- **吸量效率**：分层吸量效率（下载 ÷ 产品数），及增长 / 留存 / 变现三个效率维度；
- **新品表现**：新品渗透率、增长贡献、RPD 溢价；
- **存量表现**：成熟（1–3 年）/ 衰退（3 年以上）分层，产品年龄与下载增长的相关系数。

**运行**

```
#   目录下放 Sensor Tower 导出的榜单 csv（tab 分隔、utf-16，文件名含年份）
#   需含维度列：跑品类时用 Game Sub-genre，跑题材时用 Game Theme
#   Config.DIMENSION = "sub_genre"（品类）或 "game_theme"（题材）
python genre_analysis.py
```

输出：`game_category_analysis_report_5years.xlsx`（集中度分析 / 吸量效率分析 / 新品表现分析 / 存量产品分析 / TOP10 产品详情 5 张底表）+ CR5、吸量效率两张对比图。字段含义见 [字段说明（fields.md）](fields.md)。

**切换分析维度**：`Config.DIMENSION` 决定跑哪个维度——`"sub_genre"` 跑品类（读源列 `Game Sub-genre`），`"game_theme"` 跑题材（读源列 `Game Theme`）。换数据文件夹 + 改这一行即可，其余口径与输出结构完全一致。

## 2. market_structure_analysis.py — 趋势、产品模型、发行商与进入判断

**为什么需要**：`genre_analysis.py` 每年独立算一套指标、每行 = 维度 × 年份，**五年趋势没有被读出来**；而且细分识别只靠品类标签太粗，「进不进」的判断始终缺一个能落地的结构。

**做什么**（五张底表）

- **产品模型交叉**（替代命名聚类的细分识别）：用 Sensor Tower 官方标签 `Game Product Model`（超休闲 / 混合休闲 / 休闲 / 中重度）把品类拆开，看哪条商业化路径在增长。
  - 官方标签比自建词族簇可辩护得多。实测区分度按品类而异：合成类目超休闲占 57% / 休闲 36%（真分叉，走量 vs 走价）；卡牌与 RTS 则是 87% / 76% 集中在中重度（路径单一）。
- **五年趋势**：维度 × 年份 × 指标（CR3/5/10、分层增长贡献、新品渗透、RPD、分层吸量效率），外加**两个基准列**——相对首年、相对同组中位。没有基准，趋势表只是一堆数；有了基准才能说「在恶化还是在好转」。
- **发行商与出海**：品类内发行商集中度（Publisher CR3/CR5）、新进入者构成（新玩家 vs 老厂商跨界）、以及 `Most Popular Country by Downloads` 分布。
  - 最后一项回答一个很实的问题：美国榜单上跑得好的产品，有多少是**真靠美国市场**跑起来的（实测该字段与发行商国籍只有约 14% 一致，说明它是产品实际最畅销的市场）。
- **进入判断**：每个维度按五个固定问题各出一行结论 + 证据 + 边界——**规模够不够 / 增长正不正 / 集中度高不高 / 新品有没有空间 / 变现路径清不清晰**，最后合成「进 / 不进 / 有条件进」。
  - 阈值全部集中在 `Config`，判定依据逐条写进输出表，不用「感觉」下结论；集中度过高会触发否决项（封顶为「有条件进入」）。

**运行**

```
#   改 Config.DATA_FOLDER / OUTPUT_FOLDER / DIMENSION / RANK_AXIS
#   RANK_AXIS 必须与该数据集的排序轴一致（收入榜填 "revenue"，下载榜填 "downloads"）
python market_structure_analysis.py
```

输出：`市场结构分析_<维度>_<排序轴>_<时间戳>.xlsx`（产品模型分析 / 五年趋势 / 发行商与出海 / 市场分布 / 进入判断）。

## 3. cohort_tracking.py — 产品轨迹：进入头部、留存与换血

**为什么需要**：榜单数据最独特的能力是**用产品 ID 跨年追踪同一个产品怎么起怎么落**，而这个能力此前完全没用上。「值不值得进」里最实的一问是「进来之后能活几年」，就靠它回答。

**做什么**（四张底表）

- **队列进入率**：按首发年份分队列，看第 k 年有多少成员进入头部 Top N。
  - ⚠ 指标命名：它测的是「新品进入头部的比例」，**不是存活率**——队列成员从未被要求先进过 Top N。
  - 两个必须知道的偏误：分母是**当年进榜的新品**（不是当年全部新品）⇒ 结果偏乐观；**上线当年（k=0）在收入轴下结构性吃亏**——新游当年几乎没有收入，进不了当年收入 Top N，到第二年才有完整年度数据，所以 k=0 与 k≥1 不可直接比较。
- **头部留存**：真正的存活口径——**在首个完整经营年进入 Top N 的新品，次年还能不能保住位置**。避开「上线当年进不了榜」的干扰。
- **头部换血**：每年 Top20 里有多少是上一年不在的，换血产品里有多少是当年新品。首年无上年数据，留空而不是记成 100%。
- **存活者 vs 退出者**：把队列按次年是否仍在榜分成两组，对比它们在**进入年**的下载规模、RPD、产品模型档、发行商规模。

**运行**

```
#   改 Config.DATA_FOLDER / OUTPUT_FOLDER / DIMENSION / RANK_AXIS
python cohort_tracking.py
```

输出：`产品轨迹分析_<维度>_<排序轴>_<时间戳>.xlsx`（队列进入率 / 头部留存 / 头部换血 / 存活者vs退出者）。

## 4. concentration_cr.py — CR 集中度与 Top10 底表

**为什么需要**：报告要比较 4 国 × 4 赛道 × 5 年的下载 / 收入集中度。手工透视口径容易不一致：下载 CR 与收入 CR 须各自按下载、收入排名分别取值，当年首发的判定依赖首发日期解析。

**怎么做**

- **双排名取值**：下载 CR 按下载排名、收入 CR 按收入排名分别计算，不用同一名单；
- **CR 基数按品类切换**：Open World 产品数量少，基数取 4，其余取 5；
- **当年首发标识**：兼容多种格式的首发日期，提取年份与目标年对比，表内标黄当年首发产品；
- **两套视图**：收入维度（收入 Top10）与下载维度（下载 Top10）各一张工作表，含总量行与 CR 行。

**运行**

```
#   data/analysis_dataset.xlsx ← 合并好的分析数据集
#   需含 Unified Name / Game Sub-genre / 国家 / 年份 /
#   Downloads (Absolute) / Revenue (Absolute) / Earliest Release Date 列
python concentration_cr.py
```

输出：`data/RPG手游市场分析报告.xlsx`（4 国收入维度表 + 1 张下载专项表）。

## 5. lifecycle_classify.py — 跨年榜单分类

**为什么需要**：判断哪些产品能长期留在品类 Top20、哪些只是短暂进榜，需要逐产品的在榜年份记录；人工逐年核对效率低。

**怎么做**

- **在榜标准**：当年在本品类内下载或收入任一进入 Top20 记为在榜；
- **三分类**：始终在榜（上市以来每个有数据年份都在榜）/ 曾经在榜 / 从未在榜；
- **明细输出**：保留始终 / 曾经在榜产品，附本品类逐年排名与在榜年数。

**运行**

```
#   data/analysis_dataset.xlsx ← 同上格式的分析数据集
python lifecycle_classify.py
```

输出：`data/在榜产品分析_按品类排名.xlsx`。

## 6. 为什么没有命名聚类

曾经用产品名做过聚类（TF-IDF + K-Means，簇心 − 全局均值取词），最后整块撤掉了，原因值得记下来：

- **它测的是命名习惯，不是玩法。** 回到源数据逐个核对簇内产品后发现：某品类分出的三簇就是「名字带 War」「名字带 Battle」「其他」；某簇里一半是卡组构筑工具类 App 而不是游戏；还有个簇把数字收藏卡 App 和 roguelike 卡牌游戏放在一起。
- **词族与玩法是多对多**：一个簇混多种玩法（精度低），同一玩法被拆到几个簇（召回不全）。所以它能回答「某个命名词占多少、表现如何」，**不能回答「这个品类分成哪几条赛道」**。
- **作为归因也不成立**：没有买量投入、曝光、自然量/买量拆分数据，名字与表现之间的差异会被产品质量与发行商预算完全混淆掉。
- **它之所以被追，是因为产品名是唯一的文本字段**——工具驱动，不是问题驱动。

细分识别改由 `market_structure_analysis.py` 的**产品模型交叉**承担：官方标签、可辩护、且直接对应商业化路径。命名这件事只保留一个用途——命名词族的覆盖率可以当「定位拥挤度」的注脚。
